# Running the ONC (g)(10) test kit

The [ONC (g)(10) Standardized API Test Kit](https://github.com/onc-healthit/onc-certification-g10-test-kit)
is the certification test method for 45 CFR 170.315(g)(10). The bb tasks
below vendor it, register the OAuth clients it needs, and run its
non-interactive groups headless against either the local dromon test-server
or any FHIR server that is already running ("external target").

## Kit

`bb inferno-g10-setup` clones the kit at a pinned release tag
(`server.inferno-setup/g10-kit-tag`, currently `v8.1.0`) into the gitignored
`inferno-g10-kit/`, next to the US Core kit in `inferno-test-kit/`.

It is a separate clone, not extra gems in the US Core kit, because it pins
its own versions of the Inferno libraries:

| | g10 kit v8.1.0 | US Core kit clone |
|---|---|---|
| inferno_core | 1.6.0 | 1.0.6 |
| us_core_test_kit | 1.2.0 | 1.1.1 |
| smart_app_launch_test_kit | 1.0.3 | 1.0.0 |
| tls_test_kit | 1.0.2 | 1.0.0 |

Setup patches the kit's compose files the same way as the US Core kit's:

- The mkcert root CA is mounted and trusted.
- Host names are mapped to the host gateway.
- nginx is published on `INFERNO_G10_PORT` (default 8081; the US Core kit
  uses 8080).
- redis is not published.
- `INFERNO_HOST` is set to `http://localhost:<port>`.

Inferno derives its redirect and launch URIs from that base url:

- Redirect URI: `http://localhost:8081/custom/smart/redirect`
- Launch URI: `http://localhost:8081/custom/smart/launch`

A target served under development host names that resolve to 127.0.0.1 on
the host must have those names mapped inside the containers. Set
`INFERNO_EXTRA_HOSTS` (space or comma separated) before running
`bb inferno-g10-setup`. The patch is idempotent, so rerunning it with a
different list updates the mapping. `fhir.local` and `host.docker.internal`
are always mapped.

Start the kit with `cd inferno-g10-kit && docker compose up -d`. The web UI is
then at `http://localhost:8081/suites/g10_certification`. `bb inferno-down`
stops both kits.

## Clients

`bb inferno-g10-clients` registers five clients through the Hydra admin API
(`INFERNO_HYDRA_ADMIN_URL`). They have fixed ids, so rerunning it updates
them in place:

| client id | auth | groups |
|---|---|---|
| `inferno-g10-public` | none, PKCE S256 | public standalone launch |
| `inferno-g10-symmetric` | `client_secret_basic` | standalone, limited, v1 scopes, granular scopes |
| `inferno-g10-ehr` | `client_secret_basic` | EHR practitioner and EHR patient launch |
| `inferno-g10-asymmetric` | `private_key_jwt` ES384 | asymmetric launch |
| `inferno-g10-backend` | `private_key_jwt` ES384, `client_credentials` | Multi-Patient API (bulk) |

`INFERNO_G10_CLIENT_PREFIX` changes the `inferno-g10` prefix.

**Shared settings.**
- Every client is registered with:
  - `subject_type: public`
  - `redirect_uris` set to the redirect URI above
- The EHR client also carries `metadata.smart = {ehr_launch: true, launch_uri: <launch URI>}`.

**Keys.**
- The asymmetric client is verified with the public ES384 key of the SMART
  test kit's own key set. The task reads it from the running Inferno, so
  start the kit first.
- The backend client is verified with the public ES384 key of the g10 kit's
  committed bulk key set. The Multi-Patient API group locks the kit to that
  key set.

**Scopes.** Hydra matches a requested scope against the registered scope
string literally. Verified on Hydra v2.2.0 with the default scope strategy:
- A client registered with
  `patient/Condition.rs?category=http://terminology.hl7.org/CodeSystem/condition-category|encounter-diagnosis`
  is granted exactly that scope.
- The same client is refused another category, and is refused the
  unqualified `patient/Condition.rs`.

So every scope the suite requests is registered:
- `openid fhirUser profile launch launch/patient offline_access`
- the `read` and `rs` forms of each resource type for `patient/` and `user/`
- the `patient/*` and `user/*` wildcard forms
- the eight US Core category scopes
- for the backend client, `system/*.read system/*.rs`

**Output.**
- Client secrets are generated by the task and written to
  `inferno-g10-kit/clients.local.json` (mode 600). They are never printed.
- The task renders `inferno-custom/g10-presets/flotilla-local.json.template`
  into `inferno-g10-kit/config/presets/flotilla-local.json`. Both paths are
  gitignored.
- Rerun `bb inferno-g10-setup` afterwards to rebuild the image. The web UI
  then offers the preset "flotilla + login-consent + Hydra (local)".

When `INFERNO_KETO_WRITE_URL` is set, the backend client also gets the
type-level Keto tuples `grant-keto-permissions` writes.

## Headless runs

`bb inferno-g10` runs the runner with `INFERNO_KIT=g10` and
`INFERNO_TARGET=external`. Both can be overridden from the environment. With
no `INFERNO_GROUPS` it runs the standalone patient app (1) and EHR
practitioner app (3) groups, which need nothing but the FHIR base:

```bash
INFERNO_FHIR_URL=https://localflotilla.breezeehr.com:8444/realm/dev/fhir bb inferno-g10
```

Both groups are `run_as_group`: Inferno refuses their SMART discovery
subgroups (1.8, 3.7) on their own ("The chosen runnable must be run as part
of a group"). Run whole, each completes its discovery subgroup and then stops
at the launch with result `wait` (the authorization redirect for 1, the EHR
launch for 3). The runner prints those as `WAIT`; finish them in the web UI.
The run exits 0 whenever Inferno produced a report, 1 when it refused the
run.

| group | short id (SMART 2.2) | headless |
|---|---|---|
| Standalone patient app: discovery | 1.8, run through 1 | yes; the launch after it waits |
| EHR practitioner app: discovery | 3.7, run through 3 | yes; the launch after it waits |
| Multi-Patient API (bulk, backend services) | 8 | yes, with `INFERNO_AUTH_MODE=backend_services` |
| Standalone, limited, EHR launches; token refresh; additional authorization tests (9.x) | 1, 2, 3, 9 | no (browser) |
| Single patient API (US Core 7) | 12 | needs the token of a standalone launch |
| Visual inspection and attestations | 11 | no |

Bulk against an external target:

```bash
INFERNO_FHIR_URL=https://localflotilla.breezeehr.com:8444/realm/dev/fhir \
INFERNO_OAUTH_BASE_URL=https://localhydra.breezeehr.com:4444/ \
INFERNO_HYDRA_ADMIN_URL=https://localhydra.breezeehr.com:4445 \
INFERNO_AUTH_MODE=backend_services INFERNO_GROUPS=8 \
INFERNO_GROUP_ID=<Group id> INFERNO_PATIENT_IDS=<ids in the Group> \
bb inferno-g10
```

The runner registers a private_key_jwt client with the kit's bulk key. Set
`INFERNO_KETO_WRITE_URL` too if the target authorizes system clients through
Keto tuples.

**The bulk token URL must be the authorization server's own token
endpoint.** It defaults to `<INFERNO_OAUTH_BASE_URL>/oauth2/token`, and
`INFERNO_TOKEN_URL` overrides it. The reason:
- Hydra checks a client assertion's `aud` against its own token URL.
- So when a deployment fronts the token endpoint with a proxy on another
  host, discovery advertises the proxy, but the bulk group must still post
  to Hydra itself.

The same flow against the local dromon test-server instead:
- Boot the server, align the local Hydra issuer, start the TLS terminator,
  seed the test bundle (Group `1`, Patient `123`).
- Command: `INFERNO_KIT=g10 INFERNO_AUTH_MODE=backend_services INFERNO_GROUPS=8 bb inferno-test`.

Reports land in `target/inferno-report-g10_certification.json`.

### Suite options

`INFERNO_SUITE_OPTIONS` takes space or comma separated `option:value` pairs.
The default is:

`us_core_version:us_core_7 smart_app_launch_version:smart_app_launch_2_2 multi_patient_version:multi_patient_api_stu2`

The runner refuses a value the pinned kit does not offer. The kit offers:

| option | values |
|---|---|
| `us_core_version` | `us_core_6` (US Core 6.1.0 / USCDI v3), `us_core_7` (US Core 7.0.0 / USCDI v4) |
| `smart_app_launch_version` | `smart_app_launch_2`, `smart_app_launch_2_2` |
| `multi_patient_version` | `multi_patient_api_stu1` (Bulk Data 1.0.1), `multi_patient_api_stu2` (Bulk Data 2.0.0) |

US Core 8.0.1 is not offered by v8.1.0.

## Interactive groups

The launch groups need a browser and a user who logs in and consents. The
steps:

1. Run `bb inferno-g10-clients`, then `bb inferno-g10-setup`.
2. Open the web UI and pick the suite options above.
3. Load the preset "flotilla + login-consent + Hydra (local)".
4. Run each group from the UI.

`INFERNO_PRESET_FILE=config/presets/flotilla-local.json` makes the CLI use
the same inputs.

What the groups check, from the v8.1.0 kit source. A server has to meet these
before the interactive groups can pass.

**Discovery `capabilities`** (SMART 2.0 and 2.2):
- Standalone (1.8) requires: `launch-standalone client-public client-confidential-symmetric client-confidential-asymmetric sso-openid-connect context-standalone-patient permission-offline permission-patient authorize-post permission-v2 permission-v1`
- EHR (3.7) requires: `launch-ehr client-confidential-symmetric client-confidential-asymmetric sso-openid-connect context-banner context-style context-ehr-patient permission-offline permission-user authorize-post permission-v2 permission-v1`, plus `context-ehr-encounter` with US Core 5, 6 or 7 (`well_known_capabilities_test.rb`)

**POST authorize.**
- The EHR launch groups (3.4, 3.8) lock `auth_request_method` to `POST`.
- Every other launch uses GET.

**EHR launch token response.**
- It must contain `need_patient_banner`.
- It must contain `smart_style_url`, which Inferno fetches; it must answer
  200 with valid JSON.
- The standalone groups do not check either field.

**Token revocation (9.3).**
- The tester attests that the tokens were revoked.
- A FHIR read of `Patient/<id>` with the revoked access token must answer
  401, 403 or 404, immediately.
- A refresh with the revoked refresh token must answer 400 or 401.

## Local flotilla + login-consent + Hydra

Production serves (g)(10) from flotilla, which mounts dromon's FHIR and
SMART routes. login-consent answers Hydra's login and consent challenges and
fronts Hydra's token endpoint with a proxy that adds the launch context
(`patient`, `encounter`, `need_patient_banner`, `smart_style_url`) to the
token response. The local stack:

| service | url |
|---|---|
| flotilla FHIR base | `https://localflotilla.breezeehr.com:8444/realm/dev/fhir` |
| Hydra issuer (public) | `https://localhydra.breezeehr.com:4444/` |
| Hydra admin | `https://localhydra.breezeehr.com:4445` |
| login-consent | `https://localauth.breezeehr.com:3001` |

In production the token proxy answers on Hydra's own token URL. Locally it
is on the login-consent host, so:

- flotilla config `smart-token-endpoint` is
  `https://localauth.breezeehr.com:3001/oauth2/token`, and discovery
  advertises that URL to the launch groups.
- The bulk group still posts its `private_key_jwt` assertion to Hydra's own
  token URL, because Hydra checks the assertion's `aud` against it. The
  runner's default (`<INFERNO_OAUTH_BASE_URL>/oauth2/token`) already is that
  URL; do not set `INFERNO_TOKEN_URL` to the proxy.

The containers resolve the development host names to the host gateway, so
the three services must listen on an interface the containers reach, not only
on 127.0.0.1. Setup trusts the mkcert root CA that signs their certificates
inside the containers.

Steps:

```bash
HOSTS="localflotilla.breezeehr.com localhydra.breezeehr.com localauth.breezeehr.com"

# 1. Kit, with the local host names mapped into the containers.
INFERNO_EXTRA_HOSTS="$HOSTS" bb inferno-g10-setup
(cd inferno-g10-kit && docker compose up -d)

# 2. Clients and the preset "flotilla + login-consent + Hydra (local)".
export INFERNO_FHIR_URL=https://localflotilla.breezeehr.com:8444/realm/dev/fhir
export INFERNO_OAUTH_BASE_URL=https://localhydra.breezeehr.com:4444/
export INFERNO_HYDRA_ADMIN_URL=https://localhydra.breezeehr.com:4445
bb inferno-g10-clients
INFERNO_EXTRA_HOSTS="$HOSTS" bb inferno-g10-setup   # rebuilds the image so the preset is listed

# 3. Headless: groups 1 and 3 run their discovery subgroups (1.8, 3.7), then wait.
bb inferno-g10

# 4. Headless Multi-Patient API (8), against a Group in the dev realm.
INFERNO_AUTH_MODE=backend_services INFERNO_GROUPS=8 \
INFERNO_GROUP_ID=<Group id> INFERNO_PATIENT_IDS=<ids in the Group> \
  bb inferno-g10
```

Set `INFERNO_KETO_WRITE_URL` in steps 2 and 4 only if flotilla authorizes the
backend client through Keto tuples in the realm.

The flotilla and login-consent settings each group depends on (all default
off):

| group | needs |
|---|---|
| 1.8, 3.7 discovery | flotilla `smart-token-response-context`, `smart-launch-enabled`, `smart-style-url` and `smart-authorize-post`, so `capabilities` carries `context-banner`, `context-style`, `launch-ehr` and `authorize-post` |
| 1, 2, 9.x standalone and limited launches | the login-consent token proxy, with flotilla `smart-token-endpoint` pointing at it |
| 3.x EHR launch | flotilla launch mint (`smart-launch-enabled`), login-consent launch verification and `SMART_STYLE_URL`, and a POST `/oauth2/auth` whose `launch` reaches the consent request |
| 8 Multi-Patient API | a backend client allowed `system/*.read`, and a Group in the realm |
| 9.3 token revocation | flotilla `token-revocation-check-enabled`, so a revoked access token is refused at once |

The runner's environment is documented at the top of
`bb/src/server/inferno_runner.clj` (`runner-config`). For an external stack
on development hosts the usual set is:

| variable | example |
|---|---|
| `INFERNO_FHIR_URL` | `https://localflotilla.breezeehr.com:8444/realm/dev/fhir` |

| `INFERNO_TOKEN_URL` | omitted (Hydra's own token endpoint) |

| `INFERNO_KETO_WRITE_URL` | only when the target authorizes the backend client through Keto |

## Safety

- An external target is never booted, seeded or reconfigured, and its Hydra
  issuer is never touched.
- The dromon target refuses to start when ports 3000/3001 are taken, and
  stops only the server it launched.
- The printed `inferno execute` command redacts tokens, client secrets and
  keys.
